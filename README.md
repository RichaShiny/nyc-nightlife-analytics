# NYC Nightlife Analytics

**Do reported complaints rise around nightlife districts after midnight?** A reproducible R + Python project with an offline, interactive storytelling dashboard, based on Richa S. Tigiripally’s STA 9750 material.

## Start here

Open **[docs/index.html](docs/index.html)** in a browser. No server, API key or installation is needed. Choose year, borough, observed venue group and offense group; hover charts and map zones; switch between counts and complaints per zone/day; export the filtered data. The concluding narrative updates with your selection.

The dashboard is generated by Python from real aggregated data, with R performing cleaning and spatial analysis. It is a custom BI-style analytical report, not a Tableau/Power BI workbook.

## What the data say

The rebuilt snapshot contains **2,402,449 matched complaints** across all hours in 2019–2023. After-midnight counts are lower than early-evening counts in all observed-venue groups: **−34.1% Low, −31.1% Medium, −18.2% High**. The high group contains **only one zone**. These results do not identify visitor-adjusted risk or a causal effect of nightlife.

Read [computed findings](docs/findings.md), [research design](docs/research-design.md), [data join methodology](docs/data-join-methodology.md), [source audit](docs/source-audit.md), and [data dictionary](docs/data-dictionary.md).

## Five research questions

1. Do complaints increase from 8 PM–midnight to midnight–4 AM?
2. Do complaints fall from midnight–4 AM to 4–8 AM?
3. Does the midnight change differ by observed venue group and geography?
4. Which offense groups contribute to overnight volume?
5. Does the direction persist across 2019–2023?

## Reproduce the Python analysis and dashboard

Python 3.10+; standard library only. Run from the repository root:

```sh
python3 python/build.py
python3 -m unittest discover -s tests -v
```

Checked-in aggregate files are sufficient. The builder validates totals, calculates changes and paired-month bootstrap intervals, writes findings, and embeds the analytical cube and simplified boundaries in one offline HTML file. Edit `python/dashboard.html` for the presentation and `python/build.py` for calculations. There are no CDN dependencies.

## Rebuild from original inputs with R

R 4.5 was used with `sf`, `dplyr`, and `jsonlite`. Install these packages first:

```r
install.packages(c("sf", "dplyr", "jsonlite"))
```

```sh
Rscript R/prepare.R /path/to/original/data
python3 python/build.py
```

The source directory must contain `raw/nypd_complaints_raw.rds`, `raw/yelp_nightlife.rds`, and `raw/taxi_zones.rds`. Raw source files are not bundled. Their fingerprints are recorded in `data/processed/audit.json`. The exact venue snapshot is required for source-level reproduction; a fresh venue download is a different study, not an interchangeable substitute. Aggregate reproduction is fully available in this repository.

R removes duplicate complaint IDs, filters occurrence dates and valid hours/coordinates, dissolves taxi polygons by LocationID, assigns both venue and complaint points only when uniquely within a polygon, joins the two sources through the shared taxi-zone LocationID, classifies offenses, and exports aggregates. All eligible taxi zones remain in the denominator, including zones with no matched complaints or observed venues. No nearest-neighbor reassignment is used. See [How the data were joined](docs/data-join-methodology.md) for the full pipeline.

## Responsible interpretation

A 244-record venue snapshot is incomplete and temporally mismatched to 2019–2023. Zero observed venues is not verified absence. Group thresholds (0–4, 5–14, 15+) are counts, not venues per square kilometer. Complaint data reflect reporting and enforcement as well as underlying events. Occurrence-start times can be approximate. Population and patron exposure are missing. Do not translate these results into “safest neighborhood” rankings or policing allocation percentages.
